# Migration: ZV 0.7 → 0.8

## Summary

ZV 0.8 replaces the single-blob `cross_chunk_links/<delta>/data` array
(and its parallel `cross_chunk_link_attributes/<name>/<delta>/data`)
with a **partitioned layout** keyed by the sorted unique set of chunks
each record touches:

```
# 0.5 (legacy)
/N/cross_chunk_links/<delta>/data                                       ← single int64 blob
/N/cross_chunk_link_attributes/<name>/<delta>/data                      ← single attr blob

# 0.8
/N/cross_chunk_links/<delta>/<chunk_sorted_0>/.../<chunk_sorted_{K-1}>/data
/N/cross_chunk_link_attributes/<name>/<delta>/<chunk_sorted_0>/.../<chunk_sorted_{K-1}>/data
```

Each record's chunk coords are now implicit in the path (not repeated
inside the payload), so a `link_width=2`, `sid_ndim=3` record drops
from 64 bytes to 18 bytes; readers wanting "records between chunks A
and B" do a single sorted-path lookup instead of scanning the whole
blob.

See the [cross-chunk links spec](../object_model/cross_chunk_links.md)
for the full encoding details and worked examples.

## Compatibility

**0.5 stores are not readable by 0.8 readers without migration.** A
0.8 reader fails fast when it sees:

- A `cross_chunk_links/<delta>/data` blob (the old monolithic
  layout) under a level group.
- A `cross_chunk_links/<delta>/` group whose `.zattrs` either lacks the
  `layout` key or has `layout != "partitioned_v1"`.
- A store whose root `format_capabilities` list carries
  `multiscale_links` but not `partitioned_cross_chunk_links`.

The reader emits a clear error directing the user to run the migration
helper described below.

## Migration helper

A one-shot in-place migration utility lands alongside the 0.8 writer
changes (Phase B):

```python
from zarr_vectors.migration import partition_legacy_cross_chunk_links

partition_legacy_cross_chunk_links(store_path="path/to/store.zv")
```

What it does, level by level and `<delta>` by `<delta>`:

1. Read the legacy `cross_chunk_links/<delta>/data` byte blob and its
   `.zattrs` (`num_links`, `sid_ndim`, `level_delta`, `link_width`).
2. Decode each record into endpoints (`(chunk_coords, vertex_idx)`
   tuples).
3. Group records by `tuple(sorted(set(endpoint.chunk for endpoint in record)))`.
4. Within each group, build the per-leaf 9·L-byte records:
   - `ci_i = sorted_chunks.index(record.endpoints[i].chunk)`
   - `vi_i = record.endpoints[i].vertex_idx`
5. For `delta=0` and `link_width=2`, canonicalize each record so
   `ci = [0, 1]` (swap `vi` if the original `ci` was `[1, 0]`).
6. Write the new leaves at
   `cross_chunk_links/<delta>/<chunk_sorted_0>/.../<chunk_sorted_{K-1}>/data`
   and stamp the group `.zattrs` with `layout = "partitioned_v1"`
   (dropping `num_links`).
7. Apply the same regrouping to every parallel
   `cross_chunk_link_attributes/<name>/<delta>/data` blob.
8. After all deltas at every level have been rewritten, delete the
   legacy `data` blob and stamp `partitioned_cross_chunk_links` into
   `RootMetadata.format_capabilities` (alongside the pre-existing
   `multiscale_links`).
9. Update `zv_version` to `"0.8.0"`.

The migration is **destructive** (it removes the old blob after the
new layout is in place); back up the store first if you need a
recoverable snapshot.

## What writers should do

Phase B updates all in-tree writers
([`write_cross_chunk_links`](../../../zarr_vectors/core/arrays.py),
[`write_cross_chunk_link_attributes`](../../../zarr_vectors/core/arrays.py),
the inline-link emitters in
[`zarr_vectors/multiresolution/coarsen.py`](../../../zarr_vectors/multiresolution/coarsen.py))
to emit the new layout directly. External writers built against the
0.5 API need to:

- Compute `sorted_chunks = tuple(sorted(set(record.chunks)))` per record.
- Bucket records by `sorted_chunks` and emit one leaf per unique key.
- Pack each record as `L * uint8` followed by `L * int64` (no chunk
  coords in the payload anymore).
- Apply the `ci = [0, 1]` canonicalization rule for `delta=0` `L=2`
  records.
- Stamp the group `.zattrs` with `layout = "partitioned_v1"` and stop
  writing `num_links`.
- Add `partitioned_cross_chunk_links` to the root capability list.

## What readers should do

External readers that consumed the 0.7 single blob need to:

- Check root `format_capabilities` for `partitioned_cross_chunk_links`
  before opening; fail clearly if absent (or run the migration).
- Replace the single-blob decode loop with the K-deep leaf walk
  described in
  [Reader access patterns](../object_model/cross_chunk_links.md#reader-access-patterns).
- Use `len(leaf_bytes) / (9 * link_width)` to compute per-leaf record
  counts (no more group-level `num_links`).
- Decode each record as `L * uint8` chunk-indices followed by
  `L * int64` vertex indices; recover endpoint chunks via the leaf
  path's K sorted segments and the record's `ci` permutation.
